# Monokle repository guide

`src/` contains the React UI and `electron/` the desktop main process; tests and supporting packages/configuration cover Kubernetes resource workflows. Use the pinned Node 18.17.0 from `.nvmrc`/`.node-version` and the npm lockfile. `npm ci` runs lifecycle hooks, including patch-package, Electron native dependency setup, and Husky preparation; native builds may need Python/compiler prerequisites.

Root scripts include `npm test` (Craco, non-watch), `npm run lint`, `npm run stylelint`, and `npm run build` for the renderer. `npm run electron:build:ci` also compiles Electron code; the renderer build alone does not cover it. `npm run dev` starts Electron development. `npm run ui-test` requires a packaged app under `dist/`, not just the renderer or Electron compilation; CI runs `electron-builder --publish never` after `npm run electron:build:ci` before these tests. Packaging may have platform/signing prerequisites, and the UI environment may need an X server/browser installation. There is no separate declared typecheck command. Read packaging scripts before execution; packaging/signing/publishing is distinct from local compilation.

`tests/electronHelpers.ts` calls `deleteApplicationConfig()` before launching the packaged app: on macOS it deletes `~/Library/Application Support/monokle/config.json`, and on Windows it deletes `~/AppData/Roaming/monokle/config.json`. Run UI tests only under a disposable OS user or VM with synthetic configuration; a fixture file alone does not redirect this hardcoded home-directory deletion. The existing `.husky/pre-push` hook runs `npm run prepush` (`npm run lint`); preserve that gate.

Desktop development opens an Electron application and can discover kubeconfigs or operate clusters. Use synthetic manifests and an isolated test configuration; don't read host credentials or contact a live cluster just to validate source. For UI changes, inspect relevant resource editing, validation, error, and navigation behavior. Don't copy broad cleanup or environment-dump commands from CI into a developer checkout. Report desktop/runtime checks separately from unit/build checks.

## Completing work

Carry the authorized change through the relevant checks and repair failures it causes. Make routine, reversible implementation choices using existing patterns; ask only when missing information, a material product decision, or an authorization boundary prevents the next step. Existing authorization remains valid within its scope. If blocked, name the exact action and missing prerequisite, retain concise evidence, and continue independent work.

Choose verification proportional to the change. For instructions or prose, inspect changed paths, links, and local instruction precedence and run `git diff --check -- <changed-paths>`; don't install dependencies or run the application solely for a prose edit unless an existing mandatory gate requires setup. For behavior changes, exercise the affected behavior and applicable checks below, then broaden only for failures or unresolved risk. Report files changed, checks actually run and their results, commands only inspected, and remaining limitations. A build or source inspection alone does not prove runtime behavior. Continue through already-authorized follow-through; stop at explicit review checkpoints or boundaries requiring new authorization.
